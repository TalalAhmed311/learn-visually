Chapter 01 · OSTEP ch. 1–2

Introduction to Operating Systems

One CPU, one memory, one disk — yet dozens of programs each behave as if they own the whole machine. This chapter introduces the software that makes that work, and the three ideas the rest of the book is built on.

Beginner ~30 min C · Linux · gcc 13

Prerequisites: none in this book. You should be able to read basic C (pointers, malloc) and run commands in a Unix shell.

About this page

Based on Operating Systems: Three Easy Pieces v0.90 by Remzi & Andrea Arpaci-Dusseau, chapters 1 (dialogue) and 2. Explanations are written fresh for this guide. The book's C examples were rewritten so they build on their own (the book relies on a common.h it doesn't print) and were compiled and run on Linux x86-64 with gcc 13.3. Every output shown below comes from those real runs unless it is labelled "illustrative".

Why this matters

Every program you have ever written ran on top of an operating system, and most of its "free" behaviour came from it: your server process gets CPU time even though 300 other processes are running; two browser tabs can't read each other's memory; the file you saved is still there after a reboot. When those guarantees break, the bugs are confusing unless you know what the OS is doing underneath.

"Why is my counter wrong?"

Multi-threaded code that loses updates is a concurrency problem — you'll see it happen in this chapter with 10 lines of C.

"Why do two containers not clash?"

Each process gets a private virtual address space and a share of the CPU. Containers build on these same mechanisms.

"I saved it — why is it gone?"

write() returning doesn't mean the data reached the disk. Persistence has rules you need to know.

"Why is this syscall-heavy loop slow?"

Crossing from your program into the kernel costs far more than a function call. The boundary exists for protection.

This chapter is a guided tour. It shows you each of the book's three big ideas — virtualization, concurrency, persistence — once, with a tiny program, so that later chapters have something to hang on.

Core concepts

CONCEPT 1 / 9What "running a program" actually means

A running program does one simple thing over and over: take the next instruction, work out what it is, and do it.

The processor keeps a special register, the program counter (PC), holding the memory address of the next instruction. Each cycle it fetches the instruction at that address, decodes it (which operation? which registers?), and executes it (add numbers, read or write memory, jump somewhere else). Then the PC moves on, and the loop repeats — billions of times per second on a modern CPU.

Definition

The von Neumann model: instructions and data both live in memory; the processor repeatedly fetches an instruction from the address in the program counter, decodes it, and executes it, then advances to the next instruction.

Analogy

A cook following a recipe card: read the next line (fetch), understand it — "whisk two eggs" (decode), do it (execute), move a finger down to the next line (advance the PC). A line like "if the sauce is thick, go to step 9" is a branch.

Where it breaks down: a cook can skip ahead or do two steps at once when sensible. A real CPU also does that internally (pipelining, out-of-order execution), but it is built so that the result always looks as if instructions ran one at a time, in order. That simple sequential model is the one programs — and this book — rely on.

Here is the same program written in our toy assembly. Real assembly (x86-64, ARM) looks similar in spirit; you'll see a real x86-64 snippet in concept 5.

add.toy — illustrative ISA

LOAD  R1, [100]   ; R1 ← memory[100]  (7)
LOAD  R2, [101]   ; R2 ← memory[101]  (5)
ADD   R1, R2      ; R1 ← R1 + R2      (12)
STORE R1, [102]   ; memory[102] ← R1
HALT              ; stop
  1. L1–2Loads copy values from memory into registers — the CPU can only do arithmetic on registers in this machine.
  2. L3The arithmetic happens entirely inside the CPU; memory isn't touched.
  3. L4A store writes the result back. Keep "load → modify → store" in mind: it is exactly what goes wrong in concept 5.

⚠ Common mistake

Thinking one line of C is one machine instruction. It often isn't — and the gap matters as soon as two things run at once.

✗ Mental model
counter++;   // "one step, can't be interrupted"
✓ What the CPU sees (gcc -O0, x86-64)
movl counter(%rip), %eax   # load
addl $1, %eax              # add
movl %eax, counter(%rip)   # store
Under the hood: is it really one at a time? advanced

No. Modern processors overlap many instructions (pipelining), issue several per cycle (superscalar), and even run them out of order, then "retire" results in program order. The book deliberately ignores this: it is the hardware's job to preserve the illusion of sequential execution for a single thread. The OS cares about the illusion, not the tricks. If you're curious about the tricks, Inside the Machine (another book in this library) covers them.

CONCEPT 2 / 9What an operating system is — three roles

The OS is the body of software that makes the machine easy to use and safe to share.

The book describes the same software from three angles. They aren't three different components — they are three ways of looking at one job:

1 · A virtual machine

It takes a physical resource (CPU, memory, disk) and turns it into a more general, more powerful, easier-to-use virtual version. That's why the OS is sometimes called a virtual machine.

2 · A standard library

It exports a few hundred system calls — run a program, allocate memory, open a file — that every application can use.

3 · A resource manager

CPU time, memory and disk are shared. The OS decides who gets what, aiming to be efficient, fair, or whatever goal the system has.

Definition

An operating system is software that (a) virtualizes physical resources, (b) provides an interface of system calls through which programs use them, and (c) manages those resources among competing programs, while keeping the system correct and efficient. The always-resident, privileged core of it is called the kernel.

Analogy

A hotel. Each guest gets what feels like a private room with its own key (virtualization). Guests don't wire their own electricity — they call the front desk (system calls). Management decides who gets which room and when the cleaners come (resource management).

Where it breaks down: hotel rooms really are separate physical rooms. With virtualization there is often only one real resource — one CPU — and the "private copy" is an illusion created by switching very quickly between guests.

A useful pair of words appears here for the first time and runs through the whole book. A mechanism is how something is done (e.g. how to stop one program and start another). A policy is the decision of which (e.g. which program should run next). Keeping them separate lets you change the decision without rewriting the machinery.

You can watch the "standard library" role directly. printf is not a system call — it's a C library function that eventually calls the write system call. strace prints every system call a program makes:

terminal — real run
$ cat hello.c
#include <stdio.h>
int main(void) { printf("hello\n"); printf("world\n"); return 0; }
$ gcc -o hello hello.c
$ strace -e trace=write ./hello > /dev/null
write(1, "hello\nworld\n", 12)          = 12
+++ exited with 0 +++
  1. L3Two separate printf calls in the source…
  2. L6…but only one write system call. libc buffered both strings in the program's own memory and handed them to the kernel together (stdout was redirected to a file, so it is fully buffered; on an interactive terminal libc flushes per line instead).

⚠ Common mistake

Confusing the OS with the programs that ship with it. Your shell, file manager and desktop are ordinary user programs. The "OS" in this book mostly means the kernel: the code that runs with full hardware privileges.

✗ Wrong

"bash is the operating system — it runs my programs."

✓ Right

"bash is a user program. It asks the kernel to create and run processes via system calls (fork, exec, wait — Chapter 03)."

CONCEPT 3 / 9 · VIRTUALIZATIONVirtualizing the CPU

With one physical CPU, the OS can make many programs appear to run at the same time.

The book's first program, cpu.c, does almost nothing: it burns about one second of time, prints a string you gave it, and repeats forever. Run one copy and you get a boring column of A's. Run four copies on a single-CPU machine and all four make progress — their output interleaves. Each program behaves as if it had its own processor.

Definition

Virtualizing the CPU means turning a single CPU (or a few) into the illusion of a practically unlimited number of virtual CPUs, so many programs can seemingly run at once. The OS does it with help from hardware by time sharing: running one program for a short while, stopping it, running another, and so on. Which program runs next is decided by a scheduling policy.

Analogy

A chess master playing a simultaneous exhibition against 20 people. They walk from board to board making one move at each. Every opponent experiences a full game against the master, even though there's only one master.

Where it breaks down: the master keeps each game's position in their head and sees it on the board. A CPU has no memory of a paused program — the OS must explicitly save its registers and restore them later (a context switch, Chapter 04). And the master moves on politely; the OS must be able to take the CPU back from a program that never yields, using a hardware timer.

The program (rewritten so it builds by itself; the book's version relies on a common.h it doesn't print — ours re-creates it):

common.hre-created

#ifndef COMMON_H
#define COMMON_H
#include <sys/time.h>
#include <stdio.h>
#include <stdlib.h>
#include <assert.h>
#include <pthread.h>

/* Wall-clock time in seconds, with microsecond resolution. */
static inline double GetTime(void) {
    struct timeval t;
    int rc = gettimeofday(&t, NULL);
    assert(rc == 0);
    return (double) t.tv_sec + (double) t.tv_usec / 1e6;
}

/* Busy-wait (burn CPU) for `howlong` seconds. */
static inline void Spin(int howlong) {
    double t = GetTime();
    while ((GetTime() - t) < (double) howlong)
        ; /* do nothing in loop */
}

/* pthread_create, but abort if it fails. */
static inline void Pthread_create(pthread_t *t, const pthread_attr_t *attr,
                                  void *(*start)(void *), void *arg) {
    int rc = pthread_create(t, attr, start, arg);
    assert(rc == 0);
}

static inline void Pthread_join(pthread_t t, void **ret) {
    int rc = pthread_join(t, ret);
    assert(rc == 0);
}
#endif
  1. L10–15GetTime() reads the wall clock via the gettimeofday system call.
  2. L18–22Spin(n) loops until n seconds of wall-clock time have passed — it measures elapsed real time, not CPU time received. This matters in the gotcha below.
  3. L25–34Capitalised wrappers around pthread calls that crash loudly on error, instead of silently continuing. Used in concept 5.
cpu.clightly modernized

#include <stdio.h>
#include <stdlib.h>
#include "common.h"

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);              // burn ~1 second
        printf("%s\n", str);  // then print our label
        fflush(stdout);
    }
    return 0;
}
  1. L6–9Require exactly one argument — the label to print.
  2. L11–15Loop forever: spin ~1 s, print. Only Ctrl-C (or kill) stops it.
  3. L14Added by us: fflush pushes the line out immediately, even when output goes to a pipe (otherwise libc would buffer it — see the strace example above).

⚠ Gotchas when you try this yourself

1 · Shell syntax. The book's line ./cpu A & ; ./cpu B & … is written for the tcsh shell. In bash or zsh that's a syntax error.

✗ bash: syntax error
./cpu A & ; ./cpu B &
✓ bash / zsh
./cpu A & ./cpu B &

2 · You probably have many cores. The book assumes one CPU. On a 4-core laptop the four copies simply run in parallel on four cores — no illusion needed. To see real time sharing, pin them all to one core: taskset -c 0 ./cpu A & taskset -c 0 ./cpu B & (Linux).

3 · Even pinned, each still prints about once per second. That surprises people. Spin() waits for one second of wall-clock time, not one second of CPU time — so sharing the CPU doesn't slow the printing, each copy just burns less CPU per print. We verified this: two copies pinned to core 0 printed A B A B … once per second each.

Under the hood: how does the OS get the CPU back? preview of Ch. 04

When ./cpu A is running, the OS is not running — the CPU is busy executing A's instructions. So how does the OS ever get control to switch to B? The answer is a hardware timer interrupt: at boot the OS programs a timer to interrupt the CPU every few milliseconds. Each interrupt forces the CPU to jump into an OS handler (in kernel mode), which can save A's registers, pick another program (policy), restore its registers, and return into it. Chapters 04–08 cover the mechanism (limited direct execution, context switches) and the policies (FIFO, round robin, MLFQ, lottery, multi-CPU).

CONCEPT 4 / 9 · VIRTUALIZATIONVirtualizing memory

Every running program gets its own private view of memory — even when two programs use the very same address.

Physically, memory is just a big array of bytes: give an address to read, give an address and a value to write. Programs touch memory constantly — every instruction fetch is a memory read, and all data structures live there.

The book's mem.c allocates one integer, prints its address, then increments it once a second. Run two copies at the same time and something odd happens: both report the same address, yet each counts independently. If they shared physical memory, one would see the other's increments. They don't.

Definition

Virtualizing memory: each process gets its own private virtual address space, which the OS (with hardware help) maps onto the machine's shared physical memory. A memory reference inside one process cannot affect another process's address space or the OS's own memory.

Analogy

Two apartment buildings that both have an "Apartment 4B". The same address means different rooms because it is interpreted relative to a different building. Each resident only ever sees their own building's 4B.

Where it breaks down: real buildings don't move. The OS can relocate a process's data to a different physical spot — or even out to disk — without the process noticing, because every access is translated through a map the OS controls (page tables, Chapters 11–18).

⚠ Common mistake

Running the demo and seeing different addresses, then concluding "memory isn't virtualized". Modern systems turn on address-space layout randomization (ASLR), a security feature that places the heap at a random virtual address in each run. Disable it for this one experiment:

✗ ASLR on: addresses differ
./mem & ./mem &
✓ ASLR off for this run only (Linux)
setarch $(uname -m) -R ./mem &

And never print pointers with %x/%d — on 64-bit systems that truncates them. Use %p with a (void *) cast.

CONCEPT 5 / 9Concurrency — when "at the same time" goes wrong

When several things run at once and share data, the results can depend on timing — and be wrong.

Concurrency problems first appeared inside the OS itself (it juggles many processes, interrupts and devices at once). Today every multi-threaded program has them. A thread is like a function running at the same time as other functions, inside the same address space — so threads can share variables directly.

The book's threads.c starts two threads; each adds 1 to a shared counter loops times. With loops = 1000 the answer is 2000, as expected. With loops = 100,000 the answer is wrong — and different every run.

Definition

A race condition occurs when the result of a computation depends on the timing of how concurrent threads' instructions interleave. It happens here because counter++ is three instructions (load, add, store) that do not execute atomically — "all at once, with nothing in between".

Analogy

Two cashiers update a shared whiteboard tally. Each reads the number (50), adds the sale in their head (51), and writes it back. If both read 50 before either writes, the board ends at 51 — one sale vanished.

Where it breaks down: cashiers would notice each other. Threads can't — and the "moment of reading" is a single machine instruction, so the window is nanoseconds wide. That's why the bug appears only with large loop counts: you need many chances to hit the window.

threads.clightly modernized

#include <stdio.h>
#include <stdlib.h>
#include "common.h"

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    (void) arg;               // unused
    for (int i = 0; i < loops; i++) {
        counter++;            // NOT atomic: load, add, store
    }
    return NULL;
}

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: threads <loops>\n");
        exit(1);
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);
    Pthread_create(&p1, NULL, worker, NULL);
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}
  1. L5A global — every thread in the process sees the same variable. volatile stops the compiler keeping it in a register, but does not make updates atomic.
  2. L8–14Each thread runs worker: increment the shared counter loops times.
  3. L11The race lives here: three instructions, any of which can be followed by a switch to the other thread.
  4. L24–25Create two threads, both starting in worker.
  5. L26–27Wait for both to finish before printing.
terminal — real runs (4-core Linux)
$ gcc -Wall -pthread -o threads threads.c
$ ./threads 1000
Initial value : 0
Final value   : 2000
$ ./threads 100000
Initial value : 0
Final value   : 150237       # expected 200000
$ ./threads 100000
Initial value : 0
Final value   : 172953       # wrong again, differently

⚠ Common mistake

"I marked it volatile, so it's thread-safe." It isn't. volatile only forces a real memory load and store each time; the load-add-store sequence can still be interrupted. Make the increment a single indivisible operation instead:

✗ Still racy
volatile int counter = 0;
...
counter++;
✓ C11 atomic (prints 200000)
#include <stdatomic.h>
atomic_int counter = 0;
...
atomic_fetch_add(&counter, 1);

A mutex lock around counter++ also works (Exercise 4). How locks are built from hardware instructions is Chapter 22.

Under the hood: the actual instructions x86-64

We compiled threads.c with gcc -O0 -S. The body of the loop contains exactly the three-step pattern:

gcc -O0 -S threads.c (excerpt)
movl  counter(%rip), %eax   # load counter into register eax
addl  $1, %eax              # eax = eax + 1
movl  %eax, counter(%rip)   # store eax back into counter

On a multi-core machine the two threads may also run truly in parallel on different cores — both can load the same old value at the same instant. On one core, the bad interleaving needs a timer interrupt to land between the load and the store. Either way, the fix is the same: make the read-modify-write atomic.

CONCEPT 6 / 9Persistence — keeping data safe

Memory forgets everything when the power goes. Disks don't — but getting data there safely is hard work for the OS.

DRAM is volatile: a crash or power loss wipes it. To keep data, we need I/O devices — hard drives, SSDs — and software that manages them. That software is the file system.

Notice a difference from CPU and memory: the OS does not give each program a private virtual disk. Files are meant to be shared: your editor writes main.c, the compiler reads it and writes main, the shell runs main. Three processes, cooperating through files.

Definition

Persistence is storing data so it survives crashes and power loss. The file system is the part of the OS responsible for storing users' files on devices reliably and efficiently; it reaches each device through a device driver — OS code that knows that specific device's interface.

Analogy

Handing a document to a records office. You fill in a form (open, write, close) at the counter and get a receipt quickly. Behind the counter, clerks decide which cabinet and drawer it goes in, update the index cards, and eventually file it.

Where it breaks down: a receipt at a real office usually means "it's filed". Here, the "receipt" (write returning) often just means "it's in our in-tray (memory)". If the building loses power before the clerks file it, it's gone — unless you explicitly ask them to file it now (fsync).

io.cmodernized + fixed

#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>
#include <sys/types.h>

int main(void) {
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRUSR | S_IWUSR);
    assert(fd > -1);
    const char *msg = "hello world\n";
    ssize_t rc = write(fd, msg, strlen(msg));   // 12 bytes, no '\0'
    assert(rc == (ssize_t) strlen(msg));
    rc = fsync(fd);                              // ask the OS to push it to the device
    assert(rc == 0);
    close(fd);
    return 0;
}
  1. L9–10open asks the file system to create /tmp/file (or empty it if it exists — O_TRUNC), writable, readable/writable by its owner only. It returns a small integer, the file descriptor, used in later calls. The book uses S_IRWXU (also execute permission); we dropped execute since this is a text file.
  2. L11–13write hands 12 bytes to the OS and returns how many it accepted.
  3. L14–15Added by us: fsync blocks until the OS reports the data is on the device. Without it, the data may sit in memory for a while (Figure 7). The book introduces fsync in Chapter 31 (book ch. 39).
  4. L16close says we're done with this file descriptor.

⚠ Gotcha hidden in the book's version

The book's io.c calls write(fd, "hello world\n", 13). The string has 12 visible characters; the 13th byte is C's invisible string terminator '\0', which ends up in the file. We checked with od -c:

✗ book: hard-coded 13
$ od -c /tmp/file
0000000 h e l l o   w o r l d \n \0
0000015
✓ strlen(msg) = 12
$ od -c /tmp/file
0000000 h e l l o   w o r l d \n
0000014

(od prints offsets in octal: 015 = 13 bytes, 014 = 12 bytes.) Text tools mostly ignore the stray NUL, but diff, checksums and other programs won't.

Under the hood: why writes are delayed, and how crashes are survived preview of Part III

Disks are slow compared with memory, so most file systems buffer writes in memory for a while and then send them in larger batches. To survive a crash in the middle of a multi-step update, they use a careful write protocol such as journaling (write a note describing the change first, then make it) or copy-on-write (never overwrite in place). They also choose data structures — from simple lists to B-trees — so lookups stay fast. Part III of the guide (Chapters 28–41) works through devices, disks, RAID, file-system layout, crash consistency and SSDs.

CONCEPT 7 / 9 · PROTECTIONUser mode, kernel mode & system calls

A system call is not just a function call into OS code — it also flips the CPU into a more powerful mode, in a way the program can't abuse.

If the OS were just a library, any program could call the "read disk block" routine directly — and read anyone's files. So OS code must be special. The solution, pioneered by the Atlas computer, is a hardware privilege level: ordinary code runs in user mode, where it can't start I/O, touch arbitrary physical memory, or send network packets. The OS runs in kernel mode with full access.

To ask for a privileged service, a program executes a special trap instruction. The hardware simultaneously raises the privilege level and jumps to a trap handler that the OS registered at boot — the program can't choose where to land. When the OS is done, a return-from-trap instruction drops back to user mode and resumes the program right after the trap.

Definition

A system call transfers control into the OS while simultaneously raising the hardware privilege level to kernel mode, entering only at OS-chosen entry points. A procedure call just jumps to code at the same privilege level.

The measured costs above come from this micro-benchmark, run on our test machine (a sandboxed Linux container). Your numbers will differ — CPU, kernel version, security mitigations and virtualization all change them — but the gap of roughly two orders of magnitude is the lesson.

syscost.cour example

#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <time.h>

#define N 1000000

__attribute__((noinline)) long plain_function(void) {
    return 42;                 // an ordinary procedure call
}

static double now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e9 + ts.tv_nsec;
}

int main(void) {
    volatile long sink = 0;

    double t0 = now_ns();
    for (int i = 0; i < N; i++)
        sink += plain_function();
    double t1 = now_ns();
    for (int i = 0; i < N; i++)
        sink += syscall(SYS_getpid);   // forces a real trap into the kernel
    double t2 = now_ns();

    printf("procedure call: %6.1f ns each\n", (t1 - t0) / N);
    printf("system call   : %6.1f ns each\n", (t2 - t1) / N);
    return 0;
}
  1. L9–11noinline stops the compiler from deleting the call, so we really measure a procedure call.
  2. L13–17A monotonic clock (never jumps backwards) for timing.
  3. L27–28syscall(SYS_getpid) issues the raw system call. We avoid plain getpid() because some C libraries have cached its result in the past, which would skip the kernel entirely.

ORDER IT The life of a write() system call

Drag the steps (or use the ↑ ↓ buttons) into the order they happen on Linux x86-64, then check.

  1. Your code calls the C library's write() wrapper — an ordinary procedure call.
  2. The wrapper puts the system-call number and arguments into registers.
  3. The wrapper executes the trap instruction (syscall).
  4. Hardware switches to kernel mode and jumps to the handler the OS registered at boot.
  5. The kernel checks the arguments and performs the write (e.g. into the page cache).
  6. The kernel executes return-from-trap: back to user mode, result in a register.
  7. The wrapper returns the byte count to your code (or −1 and sets errno).

⚠ Common mistake

Making one system call per tiny piece of data. Each one pays the trap cost above.

✗ 1,000,000 system calls
for (i = 0; i < n; i++)
    write(fd, &buf[i], 1);
✓ 1 system call (or use stdio, which buffers)
write(fd, buf, n);

CONCEPT 8 / 9Design goals — and why they conflict

Building an OS is choosing trade-offs. These are the goals the book keeps coming back to.

Analogy

Airport security. More checks (protection) make flying safer but slower (performance). Good design finds checks that are cheap but effective — and puts them only at the boundary (the gate), not on every step inside the plane.

Where it breaks down: airports can wave trusted travellers through. An OS can't fully trust any user program — the check happens on every system call.

Example: the cost of protection, in numbers

The benchmark in concept 7 measured ~1.7 ns for a function call and ~280 ns for a system call. That ~165× difference is (part of) the price of protection. It's also why the OS's job is to make the common path fast: a program like ./cpu runs entirely in user mode, directly on the CPU, with no OS involvement until the timer fires — virtualization at near-zero overhead. Chapter 04 shows how this "limited direct execution" works.

⚠ Common mistake

✗ "The best OS maximizes every goal."

Goals pull against each other; perfection isn't attainable.

✓ "The right trade-off depends on the use."

A phone OS weighs energy heavily; a database server weighs throughput and reliability; both need protection.

CONCEPT 9 / 9A short history: how OSes got here

Each era added one idea we still use: libraries, protection, multiprogramming, UNIX's simplicity.

  • Libraries & batch processing. The first "OS" was a set of shared routines (e.g. for I/O). A human operator ran jobs one after another. Interactive use was too expensive — an idle machine wasted a fortune.
  • Protection. Once it was clear OS code must be treated differently, the Atlas system introduced the system-call idea with hardware privilege levels (concept 7).
  • Multiprogramming. Cheaper minicomputers like DEC's PDP machines put more computers in more hands. The OS kept several jobs in memory and switched to another while one waited for slow I/O — raising CPU utilization (see Lab 3). This forced the problems of memory protection and concurrency into the spotlight.
  • UNIX. Ken Thompson and Dennis Ritchie at Bell Labs took ideas from Multics (and systems like TENEX and the Berkeley Time-Sharing System) and made them simpler. Small programs connected by pipes (grep foo file.txt | wc -l), a C compiler, and readable source code shared freely made it hugely influential; Berkeley's BSD added virtual memory, file-system and networking work.
  • The PC: a step backwards. Early PC systems forgot the lessons: DOS had no memory protection, so any program could scribble over memory; Mac OS 9 and earlier used cooperative scheduling, so one program stuck in an infinite loop could hang the whole machine.
  • Modern era. The old ideas returned: Windows NT; Mac OS X with UNIX at its core; and Linux — Linus Torvalds' UNIX-like system written from scratch — which now runs most internet servers and, via Android, most phones.

Analogy

A restaurant growing up: first a shared recipe book (libraries); then a locked kitchen only staff can enter (protection); then one chef cooking several orders while sauces simmer (multiprogramming).

Where it breaks down: restaurants rarely "forget" the locked kitchen. In computing, the PC era did exactly that — new hardware, new programmers, old lessons relearned.

⚠ Common mistake

✗ "Cooperative multitasking is fine — programs yield."

One buggy loop that never yields freezes everything (classic Mac OS).

✓ Preemptive multitasking

A hardware timer interrupt lets the OS take the CPU back no matter what the program does (Chapter 04).

        Worked example: what really happens for echo hello > greeting.txt

        Let's trace one everyday shell command through all three pieces, using strace to watch every system call. (Real output from Linux; noise from loading the C library trimmed.)

        terminal — real run
        $ strace -f -e trace=openat,write,close,dup2,fcntl sh -c 'echo hello > /tmp/greeting.txt'
openat(AT_FDCWD, "/tmp/greeting.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
fcntl(1, F_DUPFD, 10)                   = 10
close(1)                                = 0
fcntl(10, F_SETFD, FD_CLOEXEC)          = 0
dup2(3, 1)                              = 1
close(3)                                = 0
write(1, "hello\n", 6)                  = 6
dup2(10, 1)                             = 1
close(10)                               = 0
+++ exited with 0 +++
$ strace -e trace=openat,read,write,close cat /tmp/greeting.txt
openat(AT_FDCWD, "/tmp/greeting.txt", O_RDONLY) = 3
read(3, "hello\n", 131072)              = 6
write(1, "hello\n", 6)                  = 6
read(3, "", 131072)                     = 0
close(3)                                = 0
        1. L1Virtualizing the CPU. sh is a process. While it runs, so do hundreds of others; the scheduler gives each a slice of CPU time. It never notices.
        2. L2Persistence via a system call. The > redirection makes the shell open the file for writing, creating or truncating it. The kernel's file system finds or creates the file and returns file descriptor 3.
        3. L3–6The shell saves its real stdout (fd 1) as fd 10, then uses dup2(3, 1) so that fd 1 now refers to the file. Anything written to "standard output" now lands in greeting.txt.
        4. L7The actual write. echo is built into this shell, so no new program starts — the shell itself calls write(1, …). The 6 bytes are copied out of the shell's virtual address space into the kernel's page cache. Returns 6 immediately.
        5. L8–9Restore the original stdout and clean up. Note there was no fsync: the data is probably still only in memory.
        6. L12–16Sharing through files. A different process, cat, opens the same file and reads the 6 bytes. It gets them even if they haven't reached the disk yet — the kernel serves them from the page cache. Files are shared, not virtualized.

        Putting it together

        • Virtualization: sh and cat each ran as if they had the CPU and memory to themselves.
        • Protection: every file access went through a system call (trap into kernel mode) — neither program touched the disk directly.
        • Concurrency: if two shells appended to the same file at once, their writes could interleave — the same kind of problem as threads.c, one level up.
        • Persistence: the file exists on disk only after the kernel's delayed writeback (or an explicit fsync/sync).

        Key takeaways

        • A running program just fetches, decodes and executes instructions. The OS is the software that makes running many programs easy, safe and efficient.
        • The OS plays three roles at once: virtual machine (virtualization), standard library (system calls), resource manager (sharing CPU, memory, disk).
        • CPU virtualization = time sharing: one CPU, many programs, switching fast. Mechanisms do the switching; policies pick who runs.
        • Memory virtualization = a private address space per process; the same virtual address in two processes means different physical memory.
        • Concurrency bugs arise when non-atomic operations (like counter++ = load, add, store) interleave. volatile doesn't fix them; atomics and locks do.
        • Persistence is the file system's job. write() returning ≠ data on disk; fsync() forces it.
        • System calls trap into kernel mode at OS-chosen entry points. That boundary provides protection — and costs far more than a function call.
        • OS design is trade-offs: abstraction, performance, protection, reliability, energy, security, mobility.

        Practice

        Easy → hard. Try each before opening the hint; open the solution only after you've committed to an answer.

        Exercise 1 · Mechanism or policy? easy

        Classify each: (a) saving a program's registers when it's paused; (b) "run the job with the least remaining work next"; (c) the trap instruction; (d) "when memory is full, evict the page used least recently"; (e) a hardware timer that interrupts every few ms.

        Hint

        Ask: is this how something is done, or a decision about which/when?

        Solution

        (a) mechanism (context switch), (b) policy (it's a scheduling decision — SJF/STCF, Ch. 05), (c) mechanism, (d) policy (LRU replacement, Ch. 18), (e) mechanism (it enables the OS to make policy decisions, but makes none itself).

        Exercise 2 · Share one core easy

        On Linux, run four copies of cpu.c pinned to one core: taskset -c 0 ./cpu A & taskset -c 0 ./cpu B & taskset -c 0 ./cpu C & taskset -c 0 ./cpu D &. Predict: how often does each letter appear? Then run top — what %CPU does each process get?

        Hint

        Re-read what Spin() measures: wall-clock time or CPU time?

        Solution

        Each letter still appears about once per second, because Spin(1) waits until 1 s of wall-clock time has passed. But top shows each process at roughly 25% CPU: the core is time-shared four ways. Each copy simply does a quarter of the spinning work per second. (Stop them with pkill cpu.)

        Exercise 3 · Same address, or not? medium

        Run two copies of mem.c normally (./mem & ./mem &), then again with setarch $(uname -m) -R. Explain both results. Does ASLR change whether memory is virtualized?

        Hint

        Separate two questions: which virtual address the heap starts at, and which physical memory a virtual address maps to.

        Solution

        With ASLR, each process's heap starts at a random virtual address, so the printed addresses differ. With ASLR disabled, both print the same address. In both cases each process counts independently, because each has its own address space mapped to different physical memory. ASLR only changes the virtual layout (to make attacks harder); it doesn't create or remove virtualization.

        Exercise 4 · Fix the race two ways medium

        Fix threads.c (a) with a pthread_mutex_t and (b) with a C11 atomic_int. Verify both print 2,000,000 for ./threads 1000000, and time them with time. Which is faster, and why might that be?

        Hint

        Lock: pthread_mutex_lock(&m); counter++; pthread_mutex_unlock(&m);. Compile with -pthread.

        Solution
        threads_mutex.c (worker only)
        
int counter = 0;                               // no volatile needed
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *worker(void *arg) {
    (void) arg;
    for (int i = 0; i < loops; i++) {
        pthread_mutex_lock(&lock);     // one thread at a time past here
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

        The atomic version is shown in the concept 5 gotcha. Our measurements for N = 1,000,000 on a 4-core machine (illustrative — yours will differ):

        versionfinal valuereal time
        racy volatile int1,522,4420.006 s
        atomic_fetch_add2,000,0000.027 s
        mutex2,000,0000.119 s

        Correctness costs time. The atomic version uses a single hardware read-modify-write instruction. The mutex does more work per increment, and when the two threads contend for it the lock may make a thread sleep in the kernel (note the nonzero sys time we saw for it). Chapter 22 explains how locks work inside.

        Exercise 5 · Measure the boundary hard

        Build and run syscost.c from concept 7. Then modify it to time clock_gettime() 1,000,000 times. On Linux x86-64 it's usually far cheaper than syscall(SYS_getpid) even though it "asks the OS for the time". Find out why, and explain what that says about the cost of protection.

        Hint

        Look up "vDSO" in man 7 vdso. What would need to be true for the kernel to share the current time with a process without a trap?

        Solution

        On Linux, clock_gettime is normally served by the vDSO (virtual dynamic shared object): a small piece of kernel-provided code and read-only data mapped into every process. The kernel keeps the time information in that shared page up to date, and the C library reads it in user mode — no trap, so it costs closer to a function call. This works only because reading the time is harmless: there's nothing to protect, so no privilege change is needed. Anything that must be checked or that touches shared resources (files, other processes, devices) still pays for the trap. Lesson: the OS avoids crossing the boundary when it safely can, because crossing is expensive.

        Self-check quiz

        Which of these is not one of the book's "three easy pieces"?
        The three pieces are virtualization, concurrency and persistence. The book treats security only in the sense of protection between programs and users.
        Two copies of mem.c (ASLR off) both print the same address for p, yet count independently. Why?
        That's memory virtualization: private address spaces, translated by the OS and hardware onto shared physical memory.
        What does ./threads 100000 (the racy version) print as its final value? 
        Initial value : 0
Final value   : ???
        Lost updates can only reduce the total, and how many are lost depends on timing — e.g. we saw 150,237 and then 172,953. Occasionally you even get 200,000.
        What is the key difference between a system call and a procedure call?
        The trap simultaneously jumps into the OS and switches to kernel mode; return-from-trap reverses both. That's what makes protection possible.
        "If two programs are ready, which one should run?" The answer to this question is a …
        Decisions about which are policies; the machinery for switching (how) is the mechanism.
        The book's io.c runs write(fd, "hello world\n", 13). What does wc -c /tmp/file print afterwards?
        13: the 12 visible characters plus the string's terminating '\0'. The file is visible to other programs immediately (from the page cache), even before it reaches the disk.
        write() returned 12 a moment ago; then the machine loses power. Is the data safely on disk?
        File systems delay writes to batch them for performance. write returning means the OS has the data, not that the device does.
        Why does the book call early PC operating systems like DOS "a great leap backwards"?
        DOS let any program write anywhere in memory; classic Mac OS used cooperative scheduling. The ideas returned later (Windows NT, Mac OS X, Linux).

        Glossary

        address space
        The private range of virtual addresses a process sees, holding its code, heap and stack.
        ASLR
        Address-space layout randomization: placing a process's stack, heap and libraries at random virtual addresses each run, to make attacks harder.
        atomic
        Happening all at once or not at all, as seen by everyone else; nothing can observe or interleave with a half-done atomic operation.
        batch processing
        Early mode of computing: an operator ran a set ("batch") of jobs one after another, with no interactive use.
        concurrency
        Several activities in progress at the same time (interleaved or truly parallel), and the problems that arise when they share data.
        context switch
        Saving the registers of the running program and restoring another's, so the CPU can switch between programs.
        device driver
        OS code that knows how to operate one specific kind of device.
        file system
        The part of the OS that stores files on persistent devices reliably and efficiently.
        fsync
        System call that blocks until the file's buffered data has been written to the storage device.
        journaling
        Crash-safety technique: first write a log record describing an update, then perform the update, so a crash can be repaired from the log.
        kernel
        The core of the OS, which runs in kernel mode with full access to the hardware.
        kernel mode
        Privileged CPU mode in which all instructions, I/O and memory are available. The OS runs here.
        mechanism
        A low-level method that implements a piece of functionality — the "how" (e.g. switching between programs).
        multiprogramming
        Keeping several jobs in memory and switching among them, e.g. while one waits for I/O, to keep the CPU busy.
        operating system
        Software that virtualizes the machine's resources, offers them through system calls, and manages them among programs — making the system easy to use, correct and efficient.
        page cache
        Kernel memory holding recently used file data; writes land here first and are flushed to the device later.
        PID
        Process identifier: a number unique to each running process.
        policy
        An algorithm that makes a decision using mechanisms — the "which" (e.g. which program runs next).
        process
        A running program: its address space, registers and OS bookkeeping (Chapter 02).
        race condition
        A bug where the result depends on the timing of how concurrent operations interleave.
        system call
        A request to the OS made via a trap, which enters the kernel at a fixed entry point and raises the privilege level.
        thread
        One stream of execution. Threads in the same process share its address space.
        trap
        Instruction (or event) that transfers control into the OS while switching to kernel mode.
        trap handler
        OS code, registered with the hardware at boot, that runs when a trap occurs.
        user mode
        Restricted CPU mode for applications: no direct I/O, no access to arbitrary memory.
        virtualization
        Turning a physical resource into a more general, easier-to-use virtual form — often the illusion that each program has its own copy.
        volatile memory
        Storage that loses its contents when power is lost, such as DRAM. (Unrelated to C's volatile keyword.)
        von Neumann model
        Computer model in which instructions and data share memory and the CPU repeatedly fetches, decodes and executes instructions.
