Interlude: Process API

UNIX creates processes with two odd system calls: fork() copies the caller, exec() replaces it with another program, and wait() waits for it to finish. Splitting them is what makes shells, redirection and pipes easy.

Beginner ~30 min C · Linux · gcc 13

Prerequisites: Ch. 02 — The Process (machine state, process API, states, zombies) and the file descriptors from Ch. 01.

About this page

Based on Operating Systems: Three Easy Pieces by Remzi & Andrea Arpaci-Dusseau, chapter 5. Explanations are written fresh for this guide. The book's p1.c–p4.c are lightly modernized (unused argc/argv removed, error checks after exec added, array initializers instead of strdup); the other programs are ours. Everything was compiled and run on Linux x86-64 with gcc 13.3; outputs come from those runs.

Why this matters

This is the most practical chapter so far: these calls are what every shell, build tool, process supervisor and web server worker pool is made of.

How does > file work?

The shell rewires the child's file descriptors between fork and exec. You'll see it line by line.

How does a | b work?

Two children, one kernel pipe, two dup2 calls. You'll build one in 25 lines of C.

"My output printed twice!"

A real bug caused by fork copying unflushed printf buffers. We hit it while preparing this page.

Big-picture map

Core concepts

Concept 1 / 6fork(): the process copies itself

One call goes in, two calls come out: fork() returns once in the parent and once in a brand-new child.

fork() creates a new process that is an almost exact copy of the caller: same code, a copy of its memory, same register values, same open files. The new process — the child — doesn't start at main(). It comes to life inside fork(), as if it had made the call itself, and both processes continue from the line after it.

The only way to tell them apart is the return value: the parent gets the child's PID, the child gets 0, and on failure the parent gets −1 and no child exists.

The crux

What interfaces should the OS present for process creation and control, and how should they be designed to be both easy to use and powerful?

Definition

pid_t fork(void) creates a child process with its own copy of the caller's address space, registers and file-descriptor table. It returns the child's PID in the parent, 0 in the child, or −1 (in the parent) on error.

Analogy

Photocopying a half-filled form. Both copies have exactly the same answers so far, and each can continue to be filled in differently. Someone stamped "ORIGINAL" or "COPY" on each — that's the return value.

Where it breaks down: a photocopy shares nothing with the original. A forked child does share some things: open files point to the same kernel file objects (including the current file offset), so writes from both land in the same file.

p1.cbook Fig. 5.1, lightly modernized

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    printf("hello world (pid:%d)\n", (int) getpid());
    int rc = fork();
    if (rc < 0) {                 // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {         // child (new process)
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {                      // parent goes down this path
        printf("hello, I am parent of %d (pid:%d)\n", rc, (int) getpid());
    }
    return 0;
}
  1. L6Runs once — only the original process exists yet.
  2. L7From here on there are two processes, both about to return from fork() with different rc values.
  3. L8–10−1: no child was created (e.g. too many processes).
  4. L11–12Only the child sees 0. Its own PID comes from getpid().
  5. L13–15The parent sees the child's PID — that's how it can later wait for or signal it.

"hello world" printed once: the child never ran line 6. And the child really has its own copy of memory — same variable, same virtual address, different values:

copy.cour example

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int x = 100;
    int rc = fork();
    if (rc == 0) {                 // child
        x = x + 1;
        printf("child : x = %d at %p\n", x, (void *) &x);
    } else {                       // parent
        wait(NULL);
        x = x - 1;
        printf("parent: x = %d at %p\n", x, (void *) &x);
    }
    return 0;
}

⚠ Common mistake

Not checking for −1, or treating any non-zero value as "parent". On failure there is no child, and code that later calls wait() or kill(rc, …) with −1 does surprising things (kill(-1, sig) signals every process you're allowed to signal).

✗ Ignores failure
if (fork()) {
    /* "parent" — also runs on error! */
}
✓ Three cases
pid_t rc = fork();
if (rc < 0)       { perror("fork"); exit(1); }
else if (rc == 0) { /* child  */ }
else              { /* parent */ }
Under the hood: copying a whole address space sounds slow advanced

It would be, so modern kernels don't copy eagerly. They use copy-on-write: parent and child initially share the same physical pages, marked read-only; a page is copied only when one of them writes to it. A fork() immediately followed by exec() therefore copies almost nothing. Copy-on-write appears in this guide with the VAX/VMS chapter (Ch. 19). Linux implements fork() on top of a more general call, clone(), and POSIX also offers posix_spawn(), which combines create-and-run in one call.

Concept 2 / 6Who runs first? Nondeterminism

After fork() there are two ready processes. Which one runs next is the scheduler's choice, not yours.

The book shows p1 printing the parent's line first in one run and the child's line first in another. Both are correct. On our Linux test machine the parent happened to print first in all 40 runs we tried — Linux tends to let the parent keep running — but nothing guarantees it, and it can differ under load, on another kernel, or on another OS.

Definition

A program is nondeterministic when the same input can produce different outputs or orderings from run to run, here because the order in which the scheduler runs the processes varies.

Analogy

Two runners told "go" at the same moment by the same starter. Who reaches the finish first depends on things neither controls.

Where it breaks down: runners at least start together. On one CPU only one process can run at a time; the order is entirely a scheduling decision, and on many CPUs they really can run at the same instant.

Example: a test that checks p1's output line by line would pass on our machine thousands of times and then fail somewhere else. If order matters, enforce it — usually with wait().

⚠ Common mistake

✗ "It always printed in this order on my laptop."

Observed order is not guaranteed order.

✓ Synchronize explicitly

Use wait() (or pipes, signals, locks…) to make an ordering you depend on certain.

Concept 3 / 6wait(): wait for a child to finish

wait() blocks the parent until one of its children exits, then reports which one and how.

Add wait(NULL) in the parent's branch and the output becomes deterministic: if the child runs first, it prints first; if the parent runs first, it immediately blocks in wait() until the child has printed and exited. Either way, the child's line comes first. wait() is also what reaps the zombie from Ch. 02.

Definition

pid_t wait(int *status) blocks until any child of the caller terminates, reaps it, and returns its PID (or −1 if the caller has no children). waitpid(pid, &status, options) waits for a specific child and supports options such as WNOHANG (don't block). Macros such as WIFEXITED/WEXITSTATUS and WIFSIGNALED/WTERMSIG decode the status.

Analogy

Dropping your car off for a repair and sitting in the waiting room. You can't drive off until the mechanic calls your name and hands you the report (the exit status).

Where it breaks down: plain wait() answers for any of your children, not a particular one — like being handed whichever car is ready first. Use waitpid() to wait for a specific child.

p2.cbook Fig. 5.2, lightly modernized

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    printf("hello world (pid:%d)\n", (int) getpid());
    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {         // child
        printf("hello, I am child (pid:%d)\n", (int) getpid());
    } else {                      // parent waits for the child to finish
        int wc = wait(NULL);
        printf("hello, I am parent of %d (wc:%d) (pid:%d)\n", rc, wc, (int) getpid());
    }
    return 0;
}
  1. L15The parent blocks here until the child exits. NULL means "I don't need the exit status".
  2. L16wc (the return value) equals rc: the PID of the child that finished.

And the status tells you how the child ended. Here the child calls wait() too — it has no children, so it gets −1:

waitchild.cour example

#include <stdio.h>
#include <errno.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int rc = fork();
    if (rc == 0) {                       // the child has no children of its own
        int r = wait(NULL);
        printf("child : wait() = %d (%s)\n", r, strerror(errno));
        return 7;
    }
    int status;
    int r = wait(&status);
    printf("parent: wait() = %d, child %d exited with %d\n", r, rc, WEXITSTATUS(status));
    return 0;
}
terminal — real run
$ ./waitchild
child : wait() = -1 (No child processes)
parent: wait() = 899, child 899 exited with 7

⚠ Common mistake

Reading status directly as the exit code. It's an encoded value; return 7 does not make status == 7.

✗ Raw value
wait(&status);
printf("%d\n", status);   /* 1792, not 7 */
✓ Decode it
wait(&status);
if (WIFEXITED(status))
    printf("%d\n", WEXITSTATUS(status));  /* 7 */

(On Linux the exit code sits in the second byte: 7 × 256 = 1792. Don't rely on the layout — use the macros.)

Concept 4 / 6exec(): become a different program

exec() doesn't create a process. It replaces the program running in the current one.

Given an executable and arguments, exec() loads that program's code and static data over the current ones, re-initializes the heap and stack, and starts the new program at its entry point, with the arguments as its argv. The PID stays the same, and open file descriptors stay open (unless marked close-on-exec). A successful exec() never returns — there's no old program left to return to.

Definition

The exec family replaces the calling process's program image with a new one. The underlying system call on Linux is execve(); the C library provides execl, execlp, execle, execv, execvp (and others) as front-ends. Returns only on error, with −1.

Analogy

An actor who stays on stage but switches to a completely different script mid-show. Same person (PID), same microphone (open files), entirely new lines.

Where it breaks down: an actor remembers the old play. After exec(), nothing of the old program's memory survives — only the kernel-side state such as PID, parent and open file descriptors carries over.

p3.cbook Fig. 5.3, modernized

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    printf("hello world (pid:%d)\n", (int) getpid());
    fflush(stdout);
    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {         // child: become "wc p3.c"
        printf("hello, I am child (pid:%d)\n", (int) getpid());
        fflush(stdout);
        char *myargs[] = { "wc", "p3.c", NULL };   // argv for the new program
        execvp(myargs[0], myargs);                 // only returns on error
        perror("execvp");
        exit(1);
    } else {                      // parent
        int wc = wait(NULL);
        printf("hello, I am parent of %d (wc:%d) (pid:%d)\n", rc, wc, (int) getpid());
    }
    return 0;
}
  1. L8, L15Added by us: flush stdio before fork/exec, so buffered text isn't duplicated or lost (see the gotcha below).
  2. L16The new program's argv: name, arguments, then a terminating NULL. (The book uses strdup; string literals work because execvp doesn't modify them.)
  3. L17execvp: v = arguments as a vector, p = search $PATH for wc.
  4. L18–19Added by us: reaching this line means exec failed (e.g. program not found). Without exit, the child would carry on running the parent's code.

⚠ Common mistake — output printed twice

While preparing this page we ran the book's p1.c with its output going into a pipe, and "hello world" appeared twice. printf doesn't write immediately: stdio keeps text in a buffer inside the process's memory. To a terminal it's flushed at each newline; to a file or pipe only when the buffer fills or the program exits. fork() copies the process's memory — including any unflushed buffer — so both processes later print it.

✗ Real run: ./p1 > out.txt (book's p1.c)
$ cat out.txt
hello world (pid:876)
hello, I am parent of 877 (pid:876)
hello world (pid:876)
hello, I am child (pid:877)
✓ Flush before fork() and exec()
printf("hello world (pid:%d)\n", getpid());
fflush(stdout);       /* empty the buffer first */
int rc = fork();

The same thing happens on a terminal if the text has no newline yet: our dup.c prints printf("before fork ") then forks, and the output was before fork child / before fork parent. Before exec() the opposite problem appears: unflushed text is simply lost, because the new program replaces the old buffer.

Concept 5 / 6Why separate fork and exec? The shell

Because the shell gets a moment between fork() and exec() to change the child's environment — and that one moment gives you redirection and pipes.

A shell is just a user program in a loop: print a prompt, read a command, fork() a child, have the child exec() the command, wait() for it, repeat. Since the child is still running shell code until it calls exec(), the shell can first rearrange the child's file descriptors. The new program inherits them and never knows.

  • Redirection wc p4.c > out.txt: in the child, close fd 1 (standard output), then open the file. UNIX gives a new file the lowest free descriptor, so the file becomes fd 1. wc writes to fd 1 as usual — into the file.
  • Pipes grep -o fork p1.c | wc -l: the shell creates a kernel pipe (a queue with a read end and a write end), forks two children, connects the first one's stdout to the write end and the second one's stdin to the read end (dup2), then execs both.

Definition

I/O redirection changes which file a process's standard descriptors refer to before it runs. dup2(old, new) makes descriptor new refer to the same open file as old. pipe(fds) creates a one-way in-kernel channel: bytes written to fds[1] can be read from fds[0].

Analogy

A stage manager who, after the understudy is ready (fork) but before the curtain rises (exec), quietly reroutes the actor's microphone to a recorder instead of the speakers. The actor performs as always.

Where it breaks down: rewiring a microphone is a physical act. Here it's just changing entries in the process's file-descriptor table — a few cheap system calls.

Tip — Lampson's law

The book cites Butler Lampson's design advice — "Get it right." — and argues that UNIX's simple fork/exec split is a case where the designers did.

p4.cbook Fig. 5.4, modernized

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/wait.h>

int main(void) {
    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {         // child: redirect standard output to a file
        close(STDOUT_FILENO);     // fd 1 is now free
        int fd = open("./p4.output", O_CREAT | O_WRONLY | O_TRUNC, S_IRUSR | S_IWUSR);
        if (fd != STDOUT_FILENO) { perror("open"); exit(1); }   // lowest free fd = 1
        char *myargs[] = { "wc", "p4.c", NULL };
        execvp(myargs[0], myargs);   // wc writes to fd 1 = the file
        perror("execvp");
        exit(1);
    } else {
        wait(NULL);
    }
    return 0;
}
  1. L13Only in the child: close standard output. The parent's fd 1 is untouched (separate fd tables).
  2. L14–15open returns the lowest free descriptor — 1. We check it (added by us; the book assumes it).
  3. L17wc inherits the fd table and writes its result to fd 1, i.e. the file.
terminal — real run
$ ./p4
$ cat p4.output
 24 103 738 p4.c

pipe.cour example

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

/* Runs the equivalent of:  grep -o fork p1.c | wc -l  */
int main(void) {
    int fds[2];
    if (pipe(fds) < 0) { perror("pipe"); exit(1); }   // fds[0] = read end, fds[1] = write end

    if (fork() == 0) {                    // first child: grep, writes into the pipe
        dup2(fds[1], STDOUT_FILENO);      // stdout -> pipe's write end
        close(fds[0]); close(fds[1]);
        execlp("grep", "grep", "-o", "fork", "p1.c", (char *) NULL);
        perror("exec grep"); exit(1);
    }
    if (fork() == 0) {                    // second child: wc, reads from the pipe
        dup2(fds[0], STDIN_FILENO);       // stdin -> pipe's read end
        close(fds[0]); close(fds[1]);
        execlp("wc", "wc", "-l", (char *) NULL);
        perror("exec wc"); exit(1);
    }
    close(fds[0]); close(fds[1]);         // parent must close both ends, or wc never sees EOF
    wait(NULL); wait(NULL);
    return 0;
}
  1. L9Create the pipe before forking, so both children inherit both ends.
  2. L12–13grep's stdout becomes the write end; then close the original pipe fds it no longer needs.
  3. L18–19wc's stdin becomes the read end.
  4. L23wc stops reading only when every write end is closed. If the parent kept its copy open, wc would wait forever.
terminal — real run
$ ./pipe
3
$ grep -o fork p1.c | wc -l      # the shell gives the same answer
3

⚠ Common mistake

Forgetting to close unused pipe ends. The reader gets end-of-file only once no process holds the write end open — including the parent and the reader itself.

✗ wc hangs forever
/* parent */
wait(NULL); wait(NULL);   /* fds[1] still open */
✓ Close, then wait
close(fds[0]); close(fds[1]);
wait(NULL); wait(NULL);

Concept 6 / 6Signals and other process tools

Beyond fork, exec and wait, processes are controlled by sending them signals, and observed with tools like ps and top.

The kill() system call sends a signal to a process: a small asynchronous notification such as "please terminate", "stop", "continue" or "your child exited". A process can install a handler function for most signals; when the signal arrives, the handler runs. Two signals can't be caught or ignored: SIGKILL and SIGSTOP.

SignalUsual sourceDefault actionCan be caught?
SIGINT (2)Ctrl-C in the terminalterminateyes
SIGTERM (15)kill PID (the default)terminateyes — clean up, then exit
SIGKILL (9)kill -9 PIDterminateno
SIGSTOP / SIGTSTPkill -STOP / Ctrl-Zstop (suspend)SIGSTOP no · SIGTSTP yes
SIGCONTkill -CONT, fgcontinue if stoppedyes
SIGCHLDthe kernel, when a child exitsignoredyes — handy for reaping

Definition

A signal is an asynchronous notification delivered by the kernel to a process. kill(pid, sig) sends one; sigaction() installs a handler. Numbers above are for Linux; use the names in code.

Analogy

A tap on the shoulder. SIGTERM is "please wrap up" — you can finish your sentence and leave politely. SIGKILL is security physically carrying you out.

Where it breaks down: a tap is noticed immediately. A signal is delivered when the kernel next has the chance (e.g. when the process is scheduled), and a handler interrupts whatever code was running, which is why handlers must be kept tiny.

sig.cour example

#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

static volatile sig_atomic_t got = 0;
static void on_term(int sig) { got = sig; }   // handler: just record it

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                                   // child
        struct sigaction sa = { 0 };
        sa.sa_handler = on_term;
        sigaction(SIGTERM, &sa, NULL);                // catch SIGTERM
        while (!got) pause();                         // sleep until a signal arrives
        printf("child : caught signal %d, cleaning up\n", got);
        exit(0);
    }
    sleep(1);
    kill(pid, SIGTERM);                               // polite request to stop
    int status;
    waitpid(pid, &status, 0);
    printf("parent: child exited normally? %s\n", WIFEXITED(status) ? "yes" : "no");

    pid = fork();
    if (pid == 0) { while (1) pause(); }              // a child that ignores nothing, catches nothing
    kill(pid, SIGKILL);                               // cannot be caught or ignored
    waitpid(pid, &status, 0);
    printf("parent: second child killed by signal %d\n", WTERMSIG(status));
    return 0;
}
  1. L7–8The handler only sets a flag — doing real work (like printf) inside a handler is unsafe.
  2. L13–16The child installs the handler, then sleeps in pause() until a signal wakes it.
  3. L20–21The sleep(1) gives the child time to install its handler; production code would synchronize properly instead.
  4. L26–28SIGKILL: no handler can run; the kernel ends the process. WTERMSIG reports which signal did it.
terminal — real run
$ ./sig
child : caught signal 15, cleaning up
parent: child exited normally? yes
parent: second child killed by signal 9

Useful tools: ps lists processes (ps -ef, ps -o pid,ppid,stat,cmd); top shows them live with CPU and memory use; man documents every call — the book's advice is to read the man pages (man 2 fork, man 2 wait, man 3 exec).

⚠ Common mistake

✗ Reaching for kill -9 first

The process gets no chance to flush files, remove temp files or finish a transaction.

✓ SIGTERM, then SIGKILL if needed

kill PID, wait a few seconds, and only then kill -9 PID. Service managers and container runtimes follow the same pattern.

Interactive lab

LAB Inside the shell: step through a command

Pick a command and step through the system calls a UNIX shell makes to run it. Watch the processes appear and the file-descriptor tables change. (PIDs are illustrative.)

    Worked example: a 30-line shell

    Goal. Turn the chapter into a working (tiny) shell: read a line, split it into words, run it as a command, support > file, and print the exit status. This puts fork, exec, wait and redirection together.

    minish.cour example
    
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/wait.h>

int main(void) {
    char line[256];
    while (printf("minish> "), fflush(stdout), fgets(line, sizeof line, stdin)) {
        char *argv[32], *out = NULL;
        int argc = 0;
        for (char *w = strtok(line, " \t\n"); w && argc < 31; w = strtok(NULL, " \t\n")) {
            if (strcmp(w, ">") == 0) { out = strtok(NULL, " \t\n"); break; }
            argv[argc++] = w;
        }
        argv[argc] = NULL;
        if (argc == 0) continue;
        if (strcmp(argv[0], "exit") == 0) break;      // a built-in: must run in the shell itself

        pid_t pid = fork();
        if (pid < 0) { perror("fork"); continue; }
        if (pid == 0) {                                // child
            if (out) {                                 // redirection, between fork and exec
                int fd = open(out, O_CREAT | O_WRONLY | O_TRUNC, 0644);
                if (fd < 0) { perror(out); exit(1); }
                dup2(fd, STDOUT_FILENO);
                close(fd);
            }
            execvp(argv[0], argv);
            perror(argv[0]);                           // only reached if exec failed
            exit(127);
        }
        int status;
        waitpid(pid, &status, 0);                      // parent: wait for the command
        if (WIFEXITED(status) && WEXITSTATUS(status) != 0)
            printf("[exit %d]\n", WEXITSTATUS(status));
    }
    return 0;
}
    1. L10The shell loop: prompt (flushed — no newline!), read a line, stop at end of input.
    2. L13–17Split into words; a > takes the next word as the output file.
    3. L19exit must be built in: if a child ran it, only the child would exit. (Same reason cd must be a built-in.)
    4. L21–33fork; in the child, set up redirection with dup2, then execvp. Exit code 127 is the shell convention for "command not found".
    5. L34–37The parent waits and reports a non-zero exit status.

minish> exit

    What it shows

    • Every command runs in a fresh child; the shell survives failures (nosuchcmd) because only the child exits.
    • Redirection is three lines between fork and exec — the whole point of the split.
    • Exit statuses travel from the child's exit() through waitpid to the shell (ls on a missing file exits with 2).

    Key takeaways

    • fork() creates a near-identical child; it returns the child's PID in the parent, 0 in the child, −1 on failure.
    • The child gets its own copy of memory (same addresses, independent values) but shares open files with the parent.
    • After fork(), run order is up to the scheduler — don't rely on it; use wait() to enforce order.
    • wait()/waitpid() block until a child ends, reap it, and give you its status (decode with WEXITSTATUS etc.).
    • exec() replaces the current program; the PID and open fds remain. A successful exec never returns.
    • Separating fork and exec lets the shell change the child's fds in between: that's how > and | work.
    • Flush stdio (fflush) before fork/exec, or buffered output gets duplicated or lost.
    • Signals control processes: SIGTERM asks politely, SIGKILL can't be refused.

    Practice

    Exercise 1 · Count the processes easy

    How many times does this print hi? fork(); fork(); fork(); printf("hi\n");

    Hint

    Each fork() doubles the number of processes executing the code after it. Check with the tree in concept 1.

    Solution

    2 × 2 × 2 = 8 processes, so 8 lines (in some order). In general, n sequential forks give 2n processes.

    Exercise 2 · Shared or separate? easy

    (Book homework 1–2.) After fork(): (a) if both processes change a variable x, does either see the other's change? (b) If the parent opened a file before forking, can both write to it, and what happens?

    Hint

    Run copy.c. For files, think about what the child's fd table points to.

    Solution

    (a) No — each has its own copy of memory (we saw 101 in the child and 99 in the parent). (b) Yes: both fd tables point to the same open-file object in the kernel, which holds one shared file offset. Writes from both land in the file, one after another; their order depends on scheduling, and with buffered stdio they may come out in chunks.

    Exercise 3 · Child first, without wait() medium

    (Book homework 3.) Make the child print "hello" and the parent print "goodbye", with "hello" always first — without calling wait() in the parent.

    Hint

    You need the parent to block until the child has printed. What else can block a process until another one acts? Think about this chapter's pipe example.

    Solution

    Use a pipe as a signal: create it before forking; the child prints "hello" (with fflush) and then closes its write end (or writes one byte); the parent closes its own write end and calls read() on the read end, which blocks until the child writes or every write end is closed — then prints "goodbye". sleep() in the parent is not a correct answer: it only makes the right order likely.

    Exercise 4 · Why so many exec variants? medium

    (Book homework 4.) Run /bin/ls -l from a child using execl, execlp and execv. When is each the most convenient?

    Hint

    Look at the table in concept 4: list vs vector, PATH search, environment.

    Solution

    execl("/bin/ls", "ls", "-l", (char *) NULL) — fixed arguments known at compile time, full path. execlp("ls", "ls", "-l", (char *) NULL) — same but searches $PATH, like a shell. execv("/bin/ls", argv) with char *argv[] = {"ls", "-l", NULL} — when arguments are built at run time (as in a shell). The e variants pass a custom environment. They all end up in the single execve system call; the variants are conveniences.

    Exercise 5 · Add pipes to minish hard

    Extend the worked example's minish.c so that cmd1 | cmd2 works. Make sure ls | wc -l finishes and the shell prints its next prompt.

    Hint

    Split the words at | into two argv arrays, then follow pipe.c. The shell is the parent here — what must it close before waiting?

    Solution

    Parse into left[] and right[]. Call pipe(fds). Fork child 1: dup2(fds[1], 1), close both pipe fds, execvp(left[0], left). Fork child 2: dup2(fds[0], 0), close both, execvp(right[0], right). In the shell: close both pipe fds, then waitpid for both children. If the shell keeps fds[1] open, wc never sees end-of-file and the shell hangs waiting for it — the gotcha from concept 5.

    Self-check quiz

    In the child process, what does fork() return?
    The child gets 0; the parent gets the child's PID; −1 means fork failed (and there is no child).
    What does this print? int x = 5; if (fork() == 0) { x = 10; exit(0); } wait(NULL); printf("%d\n", x);
    Only the parent prints, and it has its own copy of x, which is still 5. The child changed its copy.
    Why does adding wait() to the parent make p2's output deterministic?
    The scheduler can still pick either one; but the parent's print comes after wait() returns, which is after the child exits.
    A process calls execvp("ls", args) successfully. What happens to the line after it?
    A successful exec never returns. Code after it runs only if exec failed — which is why you put error handling there.
    Which of these does exec() keep from the old program?
    Code, data, heap and stack are replaced; kernel-side state like PID, parent and open fds (unless close-on-exec) carries over. That's what makes redirection work.
    How does wc p4.c > out.txt send wc's output to the file?
    Between fork and exec the shell closes fd 1 and opens the file (which gets fd 1), or uses dup2. wc just writes to fd 1.
    A program prints "start" with no newline, then forks; its output goes to a file. What might the file contain?
    The stdio buffer is ordinary process memory, so fork duplicates it; both processes flush their copy later. Call fflush(stdout) before fork.
    Which signal can a process not catch, block or ignore?
    SIGKILL (and SIGSTOP) always take effect. That's why it works when nothing else does — and why it gives no chance to clean up.

    Cheat sheet

    Ch. 03 · Process API

    fork

    • pid_t rc = fork();
    • rc > 0 parent (child's PID) · 0 child · −1 error
    • child: copy of memory, same fds
    • n sequential forks → 2n processes

    wait

    • wait(&s) any child · waitpid(pid, &s, 0)
    • WNOHANG = don't block
    • WIFEXITED/WEXITSTATUS
    • WIFSIGNALED/WTERMSIG
    • no children → −1 (ECHILD)

    exec

    • replaces program; keeps PID, fds
    • never returns on success
    • l = list · v = vector · p = PATH · e = env
    • execvp(argv[0], argv), argv ends with NULL

    Shell plumbing

    • loop: read → fork → (child: fds, exec) → wait
    • > f: close(1); open(f) → fd 1
    • dup2(fd, 1) · pipe(fds): [0] read, [1] write
    • close unused pipe ends!
    • cd, exit must be built-ins

    Signals

    • kill(pid, SIGTERM) · sigaction()
    • INT 2 (Ctrl-C) · TERM 15 · KILL 9
    • KILL, STOP can't be caught
    • SIGCHLD when a child exits

    Pitfalls

    • fflush(stdout) before fork/exec
    • handle exec failure: perror + exit
    • check fork() < 0
    • don't depend on run order

    Glossary

    child process
    A process created by another process (its parent) with fork().
    copy-on-write
    Sharing pages between parent and child until one writes, then copying just that page.
    dup2
    System call making one file descriptor refer to the same open file as another.
    exec
    Family of calls that replace the current program with a new one in the same process.
    file descriptor
    Small integer naming an open file in a process; 0, 1, 2 are stdin, stdout, stderr.
    fork
    System call creating a child process that is a copy of the caller.
    nondeterministic
    Able to produce different results or orderings on different runs with the same input.
    parent process
    The process that created a given child; it receives the child's PID from fork() and can wait for it.
    pipe
    In-kernel one-way byte channel with a read end and a write end, used to connect processes.
    redirection
    Making a program's standard input or output refer to a file instead of the terminal.
    shell
    A user program that reads commands and runs them using fork, exec and wait.
    signal
    Asynchronous notification sent to a process by the kernel or by kill().
    wait
    System call that blocks until a child terminates, then reaps it and returns its status.
