The Abstraction: The Process

A program on disk is just bytes. A process is that program brought to life: loaded into memory, given registers and open files, and tracked by the OS as it runs, waits and finishes.

Beginner ~30 min C · Linux · gcc 13

Prerequisites: Ch. 01 — Introduction to Operating Systems (virtualizing the CPU, mechanism vs policy, user vs kernel mode).

About this page

Based on Operating Systems: Three Easy Pieces by Remzi & Andrea Arpaci-Dusseau, chapter 3 (dialogue) and chapter 4 (the PDF pages for chapter 4 are marked version 0.91). Explanations are written fresh for this guide. All C programs here are our own; they were compiled and run on Linux x86-64 with gcc 13.3, and every output shown comes from those runs unless labelled "illustrative".

Why this matters

Every time you run a command, open an app or start a server, the OS creates a process. Most everyday operations questions are really questions about processes:

"What is this process doing?"

ps and top show a state letter — R, S, T, Z. This chapter explains what those states mean.

"Why are there <defunct> entries?"

Those are zombie processes: finished, but not yet collected by their parent. You'll create — and clean up — some.

"Why does my CPU sit idle?"

Processes that wait for disk or network are blocked. Good OSes run something else meanwhile.

"What does the kernel keep about my program?"

A record per process: its state, registers, memory, open files. Knowing it explains /proc and debuggers.

Core concepts

Concept 1 / 7Time sharing and space sharing

The OS makes one CPU look like many by taking turns. Some other resources are shared by dividing them up instead.

A typical machine seems to run tens or hundreds of programs at once, but it has only a few physical CPUs. The OS creates the illusion of a nearly endless supply of CPUs by time sharing: run one process for a little while, stop it, run another, and so on. The price is performance — if the CPU is shared, each process runs more slowly than it would alone.

The crux

How can the OS provide the illusion of a nearly endless supply of CPUs, when only a few physical CPUs exist?

Definition

Time sharing: a resource is used by one entity for a short time, then by another, and so on (CPU, a network link). Space sharing: a resource is divided into parts, each given to one user for as long as it needs it (disk blocks, memory).

Analogy

The book's dialogue uses a peach: many eaters each want their own peach, but there is only one. Since most eaters are napping most of the time, you can quietly hand the peach to whoever is awake. Each eater believes they have a peach of their own. A meeting room booked by the hour is the same idea (time sharing); a bookshelf where each person owns a shelf is space sharing.

Where it breaks down: handing over a peach is free. Switching a CPU between processes is not — the OS must save and restore state, which costs time. That overhead is why the OS can't switch infinitely often.

Time sharingSpace sharing
HowTake turns using the whole resourceSplit the resource into parts
Typical resourcesCPU, network linkDisk blocks, memory
CostSwitching overhead; each user runs slowerFragmentation; resource can fill up
OS needsA way to stop and resume users (Ch. 04)A way to track who owns which part (Ch. 13, 32)

An everyday example: run a CPU-bound program alone, then run two copies pinned to one core. Each copy takes about twice as long — the cost of time sharing.

⚠ Common mistake

✗ "Time sharing makes programs run at the same time."

On one CPU, only one process executes at any instant.

✓ "Time sharing makes programs appear to run at the same time."

They take turns fast enough that it looks simultaneous. Real parallelism needs multiple CPUs (Ch. 08).

Concept 2 / 7Mechanisms vs policies

Separate how something is done from the decision about which thing to do.

To virtualize the CPU well, the OS needs two layers. Low-level mechanisms are methods or protocols that implement a piece of functionality — for example, the context switch, which stops one program and starts another on a CPU. On top sit policies: algorithms that make decisions — for example, the scheduling policy that picks which ready process runs next, perhaps using history ("who ran most in the last minute?"), workload knowledge, or a performance goal (fast response vs. high throughput).

Definition

A mechanism answers a how question (how does the OS perform a context switch?). A policy answers a which question (which process should run right now?). Keeping them separate is a form of modularity: you can change the policy without rewriting the mechanism.

Analogy

A train network. The tracks, switches and signals are the mechanism — they can route any train anywhere. The timetable is the policy — it decides which train goes where and when. A new timetable doesn't require new tracks.

Where it breaks down: in practice the boundary leaks. Some policies need information or hooks the mechanism doesn't provide, so changing policy can still force mechanism changes.

Here's the idea in code. run_all is the "mechanism" — it repeatedly asks a policy function which process to run and runs it. Swapping the policy changes the order without touching the mechanism.

policy.cour example

#include <stdio.h>

struct proc { const char *name; int work; int done; };

typedef int (*policy_fn)(struct proc *p, int n);

/* Policy 1: first in the list that isn't finished (FIFO). */
static int pick_fifo(struct proc *p, int n) {
    for (int i = 0; i < n; i++)
        if (!p[i].done) return i;
    return -1;
}

/* Policy 2: the unfinished process with the least work (shortest first). */
static int pick_shortest(struct proc *p, int n) {
    int best = -1;
    for (int i = 0; i < n; i++)
        if (!p[i].done && (best < 0 || p[i].work < p[best].work)) best = i;
    return best;
}

/* Mechanism: repeatedly ask the policy which process to run, then run it. */
static void run_all(struct proc *p, int n, policy_fn pick, const char *label) {
    printf("%-9s:", label);
    int t = 0, i;
    while ((i = pick(p, n)) >= 0) {
        t += p[i].work;                     // "run" it to completion
        p[i].done = 1;
        printf(" %s(ends at %d)", p[i].name, t);
    }
    printf("\n");
    for (int k = 0; k < n; k++) p[k].done = 0;   // reset for the next run
}

int main(void) {
    struct proc list[] = { {"A", 30, 0}, {"B", 10, 0}, {"C", 20, 0} };
    run_all(list, 3, pick_fifo, "FIFO");
    run_all(list, 3, pick_shortest, "shortest");
    return 0;
}
  1. L3A toy process: a name, how much work it needs, and whether it's finished.
  2. L5A policy is any function that, given the list, returns the index of the process to run (or −1 if none).
  3. L8–20Two policies with the same signature: FIFO, and "shortest job first".
  4. L23–33The mechanism. It knows nothing about why a process was picked — it just runs whatever the policy names.
  5. L37–38Same processes, same mechanism, different policy → different completion times.
terminal — real run
$ gcc -Wall -o policy policy.c && ./policy
FIFO     : A(ends at 30) B(ends at 40) C(ends at 60)
shortest : B(ends at 10) C(ends at 30) A(ends at 60)

With "shortest first", B and C finish much earlier and nobody finishes later than before — a first taste of why scheduling policy matters (Ch. 05).

⚠ Common mistake

✗ Policy baked into the mechanism
void switch_to_next(void) {
    /* always pick the next one in the array */
    next = (cur + 1) % n;
    save(cur); restore(next);
}
✓ Policy passed in
void switch_to_next(policy_fn pick) {
    next = pick(list, n);   /* policy decides */
    save(cur); restore(next);   /* mechanism */
}

Concept 3 / 7What a process is: its machine state

A process is a running program — and you can describe it completely by listing the parts of the machine it can read or change.

The program itself is lifeless: bytes on disk, waiting. A process is what the OS makes of those bytes once they're running. To pin it down, take an inventory of its machine state:

  • Memory — the instructions and the data the program reads and writes. The memory a process can address is its address space.
  • Registers — many instructions read and write them. Some are special: the program counter (PC, also called the instruction pointer, IP) says which instruction runs next; the stack pointer and frame pointer manage the stack of function parameters, local variables and return addresses.
  • I/O information — for example, the list of files the process currently has open.

Definition

A process is the OS's abstraction of a running program. At any instant it is summarized by its machine state: its address space (memory), its register values (including PC and stack pointer), and its I/O state (such as open files).

Analogy

A program is a recipe in a cookbook; a process is someone actually cooking it. To pause the cook and let someone else finish later, you'd need to record everything: which step they're on (PC), what's on the counter (memory), what's in their hands (registers), which pots are on the stove (open files).

Where it breaks down: one recipe can be cooked by many cooks at once. That holds here too — run the same program twice and you get two separate processes, each with its own state. A recipe, though, never changes itself; a program's memory can.

You can see these regions in a real process by printing an address from each:

layout.cour example

#include <stdio.h>
#include <stdlib.h>

int initialized = 42;          // static data (.data)
int zeroed;                    // static data (.bss)

int main(int argc, char *argv[]) {
    int local = 7;                          // lives on the stack
    int *heap = malloc(sizeof(int));        // lives on the heap

    printf("code   (main)        : %p\n", (void *) main);
    printf("static (initialized) : %p\n", (void *) &initialized);
    printf("static (zeroed)      : %p\n", (void *) &zeroed);
    printf("heap   (malloc)      : %p\n", (void *) heap);
    printf("stack  (local)       : %p\n", (void *) &local);
    printf("argc = %d, argv[0] = %s\n", argc, argv[0]);

    free(heap);
    return 0;
}
  1. L4–5Globals live in the static-data region, loaded from (or, for zeroed ones, reserved by) the executable.
  2. L8A local variable lives on the stack, in main's frame.
  3. L9malloc hands back memory from the heap.
  4. L11The address of a function is an address in the code region. (Casting a function pointer to void * is allowed on Linux/POSIX, though not guaranteed by ISO C.)
  5. L16argc/argv were placed on the stack by the OS before main started — see concept 5.

⚠ Common mistake

✗ "A program and a process are the same thing."

Then running ./layout twice would give you one thing, not two.

✓ One program, many processes

The program is the file on disk. Each run creates a new process with its own PID, memory, registers and open files.

Concept 4 / 7The process API

Every modern OS offers some way to create, destroy, wait for, control and inspect processes.

The book defers the real UNIX calls to the next chapter, and first lists what any process interface must include. Here is that list, with the UNIX names you'll meet in Ch. 03 alongside:

OperationWhat it doesUNIX example (shell / system call)
CreateStart a new process to run a program — typing a command, double-clicking an icon../prog · fork() + exec()

Misc. controlE.g. suspend a process for a while, then resume it.kill -STOP / kill -CONT, Ctrl-Z / fg

Definition

The process API is the set of operations an OS exports for managing processes: create, destroy, wait, miscellaneous control (such as suspend/resume), and status.

Analogy

A media player's controls: play a new track (create), stop it (destroy), wait for the track to end (wait), pause/resume (control), and the progress bar (status).

Where it breaks down: a media player has one track at a time. The OS manages hundreds of processes at once, and processes can use the API on each other — a shell creates, waits for and kills its children.

All five operations, on a real Linux machine. spin is a one-line program that loops forever (int main(void) { while (1) ; }):

  2. L7–8T = stopped by a signal: suspended until someone resumes it.
  3. L11–12/proc/PID/status is a window onto the kernel's record of the process.

⚠ Common mistake

Treating a suspended process as dead. kill -STOP (or Ctrl-Z in a shell) only pauses it: it still holds its memory and open files. Resume it or end it.

Concept 5 / 7Creating a process: from program to process

Before a program can run, the OS must load it, give it a stack and heap, set up its I/O, and then jump to main().

Programs live on disk (or SSD) in an executable format. To run one, the OS does roughly this:

  1. Load code and static data into the process's address space. Early systems did this eagerly — all at once before running. Modern OSes do it lazily: they load pieces only when the program first needs them (this relies on paging and swapping, Ch. 14–17).
  2. Create the stack — memory for local variables, parameters and return addresses — and fill in main's arguments, argc and argv.
  3. Create the heap — small at first; it grows as the program calls malloc() and the OS hands over more memory.
  4. Set up I/O — on UNIX, three open file descriptors: standard input, output and error.
  5. Start running at the entry point — jump to main() through a special mechanism (Ch. 04), handing the CPU to the new process.

Definition

Process creation: the OS turns a program into a process by loading its code and static data into a new address space (eagerly or lazily), allocating and initializing the stack (with argc/argv) and heap, setting up I/O (file descriptors 0, 1, 2), and transferring control to the program's entry point.

Analogy

Setting up a stage play: bring the script and props from storage (load), clear a workspace for the actors (stack and heap), connect the microphones and lights (I/O), then raise the curtain (jump to main).

Where it breaks down: a theatre brings all props on stage before the curtain. Modern OSes deliberately don't: they fetch each piece of the program only when it's first touched, so huge programs start quickly.

You can observe step 2 from inside the program: the OS has already placed the command-line arguments on the stack before main runs.

terminal — real run (layout.c from concept 3)
$ ./layout x y
…
argc = 3, argv[0] = ./layout

⚠ Common mistake

✗ "The whole program is read into memory before it starts."

True of early systems; on a modern OS a 200 MB binary would start painfully slowly.

✓ Loaded lazily

The OS sets up the address space, then brings in each piece of code or data the first time it's touched. Parts that are never used are never read from disk.

Under the hood: what Linux actually does advanced

On Linux, a new program is started with the execve() system call (Ch. 03). The kernel reads the ELF executable's headers, sets up mappings in the new address space for the code and data segments (without copying them yet), maps a stack, copies argv and the environment onto it, and arranges for the process to start at the program's entry point — for a dynamically linked program, first in the dynamic loader, which loads shared libraries such as libc and eventually calls main. When the program first touches a code or data page that isn't in memory yet, a page fault brings it in from disk (Ch. 17).

Concept 6 / 7Process states

At any moment a process is running, ready to run, or blocked waiting for something.

  • Running — executing instructions on a processor.
  • Ready — able to run, but the OS has chosen not to run it right now.
  • Blocked — waiting for some event before it can run, e.g. it started a disk read and is waiting for the data. Meanwhile another process can use the CPU.

The OS moves processes between ready and running at its own discretion: ready → running is being scheduled; running → ready is being descheduled. Starting I/O moves a process to blocked; when the I/O completes it becomes ready again (and may or may not run immediately — the OS decides).

Definition

A process's state records whether it is running, ready or blocked. Real systems add an initial state while the process is being created and a final state after it exits but before it is cleaned up — on UNIX the zombie state.

Analogy

A doctor's office with one doctor. The patient in the exam room is running. Patients in the waiting room are ready. A patient sent off for a blood test is blocked: they can't see the doctor until the results come back, and then they return to the waiting room.

Where it breaks down: a waiting room is first-come-first-served by habit. The OS can pick any ready process it likes — that choice is the scheduling policy (Ch. 05).

The book traces two processes through these states. With CPU-only processes, one runs to completion while the other waits as ready. When Process 0 starts an I/O, the OS runs Process 1 meanwhile:

⚠ Common mistake

✗ "When the I/O finishes, the process goes straight back to running."

It goes to ready. Whether it runs immediately is a scheduling decision.

✓ blocked → ready → (later) running

The OS may keep the current process running and run the newly ready one afterwards.

Concept 7 / 7The process list and the PCB

The OS is a program too, and it keeps a data structure describing every process.

To track processes, the OS keeps a process list — all processes that are ready, plus a note of which one is running, plus the blocked ones (so that when an I/O completes, the right process can be woken and made ready). Each entry is often called a Process Control Block (PCB): a C structure holding everything the OS knows about one process.

One key field is the register context: when a process is stopped, its registers are saved there; restoring them later lets the process resume exactly where it left off. That's the heart of the context switch (Ch. 04).

Definition

A PCB (process control block) is the kernel's per-process record: state, PID, memory information, saved registers, open files, parent, and so on. The process list is the collection of all PCBs.

Analogy

A hospital ward's patient charts. Each chart (PCB) records who the patient is, their status, and exactly where treatment left off, so any nurse can pick up from there. The rack of charts is the process list.

Where it breaks down: a chart is a summary for humans. The saved register context is exact — every register value, bit for bit — or the process would resume with corrupted state.

Here is the PCB from xv6, a small teaching OS from MIT (excerpt from the book's Figure 4.5):

xv6 proc structure (excerpt, from the book)

// the registers xv6 will save and restore
// to stop and subsequently restart a process
struct context {
  int eip;   int esp;
  int ebx;   int ecx;   int edx;
  int esi;   int edi;   int ebp;

// the different states a process can be in
enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };

// the information xv6 tracks about each process
struct proc {
  char *mem;                  // Start of process memory
  uint sz;                    // Size of process memory
  char *kstack;               // Bottom of kernel stack for this process
  enum proc_state state;      // Process state
  int pid;                    // Process ID

  3. L15–16Memory: where the process's memory starts and how big it is.

The final state matters too. When a process exits, the OS keeps its PCB around as a zombie so the parent can read the exit code. The parent's wait() collects it and lets the OS free the PCB.

zombie.cour example

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();                 // create a child process (Chapter 03)
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid == 0) {                     // child
        printf("child  %d: exiting with status 3\n", (int) getpid());
        exit(3);                        // child finishes immediately...
    }
    sleep(2);                           // ...but the parent doesn't wait() yet
    printf("parent %d: child %d is now a zombie:\n", (int) getpid(), (int) pid);
    fflush(stdout);
    char cmd[64];
    snprintf(cmd, sizeof cmd, "ps -o pid,stat,cmd -p %d", (int) pid);
    system(cmd);

    int status;
    waitpid(pid, &status, 0);           // reap it: read exit code, free its PCB
    printf("parent: reaped child, exit status = %d\n", WEXITSTATUS(status));
    system(cmd);                        // the child is gone now
    return 0;
}
  1. L7fork() creates a copy of this process — preview of Ch. 03. It returns 0 in the child and the child's PID in the parent.
  2. L9–12The child prints and exits with code 3.
  3. L13–18The parent waits 2 s without calling wait(), then runs ps on the child's PID.
  4. L21–23waitpid collects the exit code; only now can the OS free the child's PCB.

⚠ Common mistake

Thinking you can kill a zombie. It has already exited — there's nothing left to kill. Only its parent can clean it up, by calling wait(). (If the parent itself exits, the orphaned zombie is adopted by an init-like process, which reaps it.)

✗ Has no effect
$ kill -9 257   # still Z
✓ Parent reaps it

Worked example: a server that leaks zombies

Scenario. A small server forks a worker process for each job. Workers finish quickly, but after a day ps shows hundreds of <defunct> entries, and eventually the server can't create new processes. What's going on, and how do we fix it?

Step 1 — Read the states. Z/<defunct> is the final state from concept 6: the worker exited, but its PCB still exists. The PCB holds the exit status until the parent asks for it.

Step 2 — Find who's responsible. Only the parent can collect a zombie (concept 7), so the bug is in the server: it never calls wait(). Each zombie still occupies a process-table slot and a PID, which is why creation eventually fails.

Step 3 — Reproduce and fix. This program starts three workers, shows them as zombies, then reaps every finished child with a non-blocking waitpid loop:

reaper.cour example

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

static void show_children(void) {
    char cmd[80];
    snprintf(cmd, sizeof cmd, "ps -o pid,ppid,stat,cmd --ppid %d", (int) getpid());
    fflush(stdout);
    system(cmd);
}

int main(void) {
    for (int i = 0; i < 3; i++) {           // a "server" starts 3 workers
        pid_t pid = fork();
        if (pid == 0) exit(i);              // each worker finishes at once
    }
    sleep(1);
    printf("before reaping:\n");
    show_children();                        // 3 zombies (plus ps itself)

    int status; pid_t done;
    while ((done = waitpid(-1, &status, WNOHANG)) > 0)    // reap every finished child
        printf("reaped %d (exit %d)\n", (int) done, WEXITSTATUS(status));

    printf("after reaping:\n");
    show_children();
    return 0;
}
  1. L14–17Three children, each exiting immediately with codes 0, 1, 2.
  2. L23–24waitpid(-1, …, WNOHANG): collect any finished child, but don't block if none is ready. Loop until there are none left.

reaped 358 (exit 0)
reaped 359 (exit 1)
reaped 360 (exit 2)
after reaping:
  PID  PPID STAT CMD
  363   357 S    sh -c -- ps -o pid,ppid,stat,cmd --ppid 357

Step 4 — Apply it to the server. A real server would run that same waitpid(-1, …, WNOHANG) loop regularly — for example each time around its main loop, or when the OS notifies it that a child exited (the SIGCHLD signal). The zombies disappear, PIDs are freed, and new workers can be created again.

What this used

  • Process states to recognize Z as "exited, not yet cleaned up".
  • The PCB to understand what a zombie still holds (exit status, a slot, a PID).
  • The process API — wait — as the cure.

Key takeaways

  • A process is a running program. A program is bytes on disk; one program can become many processes.
  • The OS virtualizes the CPU by time sharing; resources like disks are space shared. Time sharing costs some performance.
  • Mechanisms answer how (context switch); policies answer which (scheduler). Keep them separate.
  • A process's machine state = address space (code, static data, heap, stack) + registers (PC, SP, …) + I/O state (open files).
  • The process API: create, destroy, wait, control (suspend/resume), status.
  • Creation: load code and data (lazily on modern OSes), set up stack with argc/argv, heap, fds 0–2, then jump to main.
  • States: running, ready, blocked (+ initial and zombie). I/O completion makes a process ready, not running.
  • The OS tracks each process in a PCB on the process list, including its saved register context.

Practice

Easy → hard. The simulator in the lab can check exercises 2, 3 and 5.

Exercise 1 · Name the state easy

For each, give the state (running / ready / blocked / zombie): (a) a web server waiting for a request to arrive on the network; (b) a compiler that would run but another process has the CPU; (c) a child that called exit(0) whose parent hasn't called wait(); (d) a game executing its physics loop on the CPU.

Hint

Ask: is it on the CPU? If not, could it run if given the CPU?

Solution

(a) blocked — waiting for an event (network I/O); (b) ready; (c) zombie; (d) running.

Exercise 2 · CPU utilization easy

Two processes each run 4 CPU instructions and do no I/O (the Figure 4.3 preset). What fraction of the time is the CPU busy? Why can you know without simulating?

Hint

Is there ever a tick when nobody can use the CPU?

Solution

100%. With no I/O, some process is always ready, so the CPU never idles: 8 ticks of work in 8 ticks.

Exercise 3 · Does order matter? medium

P0 = cccc (CPU only), P1 = i (one I/O), I/O length 5, "switch to another process". How many ticks does it take? Now swap them: P0 = i, P1 = cccc. Predict, then check with the lab.

Hint

In which order can the I/O overlap with CPU work?

Solution

CPU first: P0 runs ticks 1–4, P1 issues its I/O at tick 5 and is blocked for ticks 6–10 with nothing else to run — 10 ticks, CPU busy 50%. I/O first: P0 issues the I/O at tick 1; while it's blocked (ticks 2–6), P1 runs ticks 2–5 — 6 ticks. Starting I/O-bound work early lets it overlap with CPU work. Choosing an order is exactly the kind of decision a scheduling policy makes.

Exercise 4 · Read the address space medium

Compile layout.c and run it three times. Which addresses change between runs? Does the order of the regions change? Then run it under setarch $(uname -m) -R and compare.

Hint

Recall ASLR from Ch. 01.

Solution

With ASLR, all addresses change between runs (the code/data base, the heap start and the stack location are each randomized), but the order — code < static data < heap, stack much higher — stays the same, because it comes from the address-space layout the OS sets up. With setarch -R the addresses repeat exactly. In our two runs above, for example, main was at 0x55667c2de1a9 and then 0x559cc359b1a9: different base, same last digits, because the offset of main inside the program doesn't change.

Exercise 5 · Run it now, or later? hard

Load "One I/O-heavy + three CPU-heavy" in the lab: P0 = iii and three processes of ccccc, I/O length 5, "switch to another process". Compare "keep running the current one" with "run the I/O process now". Which finishes sooner and keeps the CPU busier? Explain why giving the CPU to a process that just finished I/O can be a good idea.

Hint

Watch what P0 does with the CPU when it gets it. How long does it hold the CPU each time?

Solution

Keep current: P0's I/O completes at tick 7, but it waits as ready while P2 and P3 run; it only issues its next I/O at tick 17, and its last I/O ends at tick 28 — 28 ticks, CPU busy 18 of 28 (64%); ticks 18–28 the CPU mostly idles. Run immediately: each time P0's I/O completes it runs for one tick, starts the next I/O, and gives the CPU back — 18 ticks, CPU busy 100%. An I/O-bound process needs the CPU only briefly, so running it promptly keeps the device busy in parallel with the CPU work. Schedulers in Ch. 06 (MLFQ) build on exactly this observation.

Self-check quiz

What is the best short definition of a process?
The program is the lifeless file; the process is that program running — memory, registers, open files and all.
Which of these is not part of a process's machine state?
Machine state is what the running program can read or change: memory (including stack), registers (including PC), and I/O state. The source code isn't part of it.
"Which process should run next?" is answered by…
"Which" questions are policies (the scheduler). The context switch that carries out the decision is the mechanism.
A process's disk read just completed. Which state does it move to?
I/O completion makes it ready. Whether it runs right away is the scheduler's decision.
On a modern OS, how is a program's code typically brought into memory?
Early systems loaded eagerly; modern ones load lazily using paging (Ch. 14–17).
What does a freshly started UNIX process have open, without opening anything itself?
The OS sets up stdin, stdout and stderr as part of process creation.
ps shows Z / <defunct> for a process. What is true?
A zombie is the final state: exited, PCB kept for the parent. Only the parent's wait() clears it.
Why does the PCB store a copy of the process's registers?
When a process is stopped, its registers are saved in its PCB; restoring them into the CPU resumes it. That's the context switch.

Cheat sheet

Ch. 02 · The Process

Process

  • = running program + machine state
  • memory: code · static data · heap · stack
  • registers: PC (IP) · SP · FP · general
  • I/O: open files (fd 0, 1, 2 …)

Sharing

  • time sharing: take turns (CPU)
  • space sharing: split up (disk, memory)
  • mechanism = how · policy = which

API

  • create · destroy · wait · control · status
  • UNIX: fork/exec · kill · wait
  • kill -STOP / -CONT · Ctrl-Z / fg

Creation

  • load code + static data (lazily)
  • stack with argc/argv · heap
  • fds 0/1/2 · jump to main

States

  • ready → running: scheduled
  • running → ready: descheduled
  • running → blocked: start I/O
  • blocked → ready: I/O done
  • + initial · zombie (exit, until wait)

Linux

  • ps -o pid,stat,cmd
  • R runnable · S/D sleeping · T stopped · Z zombie
  • /proc/PID/status, /proc/PID/fd
  • reap: waitpid(-1, &s, WNOHANG)

Glossary

address space
The memory a process can address: its code, static data, heap and stack.
context switch
Stopping one process and starting another on a CPU, by saving the first's registers and restoring the second's.
heap
Region for memory requested explicitly at run time with malloc() and released with free().
machine state
Everything a running program can read or update: memory, registers, and I/O state such as open files.
mechanism
A low-level method or protocol implementing a piece of functionality — the "how".
PCB
Process control block: the kernel's per-process record (state, PID, memory info, saved registers, open files, parent…).
policy
An algorithm that makes a decision in the OS, such as which process runs next — the "which".
process
A running program: the OS's abstraction combining its address space, registers and I/O state.
process list
The OS data structure holding the PCBs of all processes (ready, running, blocked).
process state
Running, ready or blocked (plus initial and final/zombie on real systems).
program counter
Register holding the address of the next instruction to execute; also called the instruction pointer.
space sharing
Sharing a resource by dividing it into parts, each used by one entity (e.g. disk blocks).
stack
Region holding local variables, function parameters and return addresses; managed with the stack and frame pointers.
time sharing
Sharing a resource by letting each entity use it for a short time in turn (e.g. the CPU).
zombie
Final state of a UNIX process that has exited but whose parent hasn't yet called wait() to collect its status.
